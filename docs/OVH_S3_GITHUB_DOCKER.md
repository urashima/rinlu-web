# RINLU OVH S3: GitHub Secrets to Docker

This change delivers OVH S3 connection credentials to the existing RINLU platform Docker container, without committing keys or changing website/VPN ports. It does **not** yet implement S3 upload, playback or migration in the canonical RINLU application.

## GitHub configuration

Open https://github.com/urashima/rinlu-web/settings/secrets/actions

Create these two repository **Secrets** using values generated by OVH (do not paste them into source files, issues or chats):

- **OVH_S3_ACCESS_KEY_ID** — S3 access key ID
- **OVH_S3_SECRET_ACCESS_KEY** — S3 secret access key

Open https://github.com/urashima/rinlu-web/settings/variables/actions

Create these three repository **Variables**:

- **OVH_S3_BUCKET** — actual bucket name shown in OVH, e.g. rinlu-music-prod only if that is its real name
- **OVH_S3_REGION** — lowercase region: us-east-va for Virginia, us-west-or for Oregon
- **OVH_S3_ENDPOINT** — https://s3.us-east-va.io.cloud.ovh.us for Virginia, https://s3.us-west-or.io.cloud.ovh.us for Oregon

These are *S3-generated keys*, not the OVH account password or GitHub SSH keys. Keep existing SSH settings untouched.

## What happens on deploy

After merging the proposed change, go to https://github.com/urashima/rinlu-web/actions/workflows/deploy.yml and click **Run workflow** on main. A manual run applies updated S3 secrets even when the canonical site content is unchanged.

1. Test the secret renderer with fake credentials.
2. Validate that all five values exist and endpoint/region match. Partial configuration aborts safely.
3. Stream the env file over the existing verified SSH channel without logging key values.
4. Stage it on the VPS with 0600 file permissions.
5. The root publisher copies it into /etc/rinlu/storage.env with ownership root:root and permissions 0600, removes the staging file, and passes this as an additional --env-file to the rinlu-platform Docker container.
6. If all S3 values are absent, the deploy preserves the currently running storage configuration. Existing Google login secrets and VPN ports are unchanged.

## Verification

After a successful workflow run, connect to the VPS and execute these checks; neither prints the credential values:

    sudo test -s /etc/rinlu/storage.env && echo 'S3 file exists'
    sudo stat -c '%a %U:%G' /etc/rinlu/storage.env
    docker exec rinlu-platform sh -c 'test -n "$RINLU_S3_BUCKET" && test -n "$RINLU_S3_ACCESS_KEY_ID" && test -n "$RINLU_S3_SECRET_ACCESS_KEY" && echo "Docker S3 credentials present"'

Expected ownership/mode: 600 root:root. Seeing Docker variables does not imply the application's music files have been migrated or S3 storage works. A later storage adapter must verify S3 access using HeadBucket and a reversible test upload, then update the upload/review/playback flow.

## Key rotation and rollback

Update GitHub Secrets then manually run the deployment workflow again. Never expose the keys through Docker inspect, printenv, log output, screenshots, or chat. Use a dedicated OVH bucket-scoped access user and short-lived signed upload/playback URLs when implementing the application data plane.
